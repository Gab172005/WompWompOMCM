============================================================
A. PRODUCT VISION AND NON-NEGOTIABLE GOALS
============================================================

OMCM is a web-based decision-support platform for LGUs that recommends where to PRE-POSITION a limited number of mobile clinics across high-need barangays in Laguna. It combines illness burden/risk, population, vulnerable groups, poverty, hospital access, and flood/weather exposure into transparent need scores. A capacity-aware maximal-coverage optimization chooses clinic staging sites to serve high-priority residents within reasonable road travel times. The platform supports stable next-day schedules, public visibility, emergency simulations, and authorized overrides.

There are three core experiences:
1. ADMIN — Analyze healthcare need, run next-day optimization, compare with a baseline, simulate emergencies, approve and publish a deployment plan.
2. SIMULATOR / FLEET TRACKER — Watch up to three clinic vehicles travel on REAL ROAD-ALIGNED routes on a REAL MAP OF LAGUNA (not on a fictional canvas); inspect each vehicle's location, ETA, status, destination, and route; pause/play/reset and accelerate time; trigger scenario changes and visualize impact.
3. PUBLIC — View today's approved clinic destinations, schedules, offered services, last known position/status (when public sharing is enabled), and critical schedule or emergency advisories. Public view must never implicitly display unapproved simulations as real deployments.

Core user story for the live demo:
(a) Admin opens Laguna map showing polygons shaded light-to-dark RED by composite healthcare need.
(b) Admin selects a barangay and sees metrics, source/date badges, score components, and risk explanation.
(c) Admin enters/chooses 3 available mobile clinics and clicks OPTIMIZE TOMORROW.
(d) App selects up to three feasible staging sites on actual mapped locations, draws routes and coverage, and displays clear reasons for each recommendation.
(e) Admin opens deployment simulation and presses PLAY. Three vehicle icons MOVE ALONG THE ACTUAL ROAD POLYLINES toward their recommended destinations, with independent progress, ETA, and status indicators, like a delivery/fleet-tracking application.
(f) Admin switches on flood / road-closure scenario or disease surge, sees impacted roads/sites and degraded coverage, then clicks REOPTIMIZE. System recomputes feasible recommendations; it does not merely change labels or randomize pins.
(g) Admin reviews changes and explicitly APPROVES/PUBLISHES the next-day plan. Public page now displays only that approved plan.
(h) Admin sees evaluation vs a simple baseline that sends clinics to the most populated barangays, including prioritized residents served, average modeled road travel time, unserved priority population, and flood-safe accessibility.

The application must be immediately understandable to a hackathon judge watching a 3–5 minute demo.

H. GENUINE CLINIC LOCATION OPTIMIZATION
============================================================

Implement a simplified but mathematically meaningful maximal covering location problem (MCLP) / capacity-aware facility-location optimizer using OR-Tools where available; deterministic reference heuristic fallback only if documented.

Inputs:
- Demand nodes: actual pilot barangay locations or population-weighted centroids.
- Each node has priority-weighted demand or estimated high-risk resident count.
- Candidate sites: geographically real and eligible, preferably barangay halls / RHUs / schools; exclude flooded/ineligible sites when scenario active.
- K clinics (default 3), capacity per clinic, available services, maximum ROAD travel time to serve a barangay (e.g. configurable 30 minutes), and travel-time matrix computed via Google Routes API or cached demonstrative route fixture from a real routing provider. Display a clear modeled/demo status if route data is approximated.

Optimization requirements:
- Select no more than K unique feasible staging sites.
- Assign demand to sites within travel-time threshold, respecting site/clinic capacity; avoid double-counting people served. If splitting demand across sites is supported, make it explicit; otherwise use a documented assignment approximation.
- Maximize total priority-weighted residents served; tie-break by shorter travel time or equitable underserved coverage. Where possible, favor smaller high-need barangays so raw population is not the sole determinant.
- Surface unserved barangays and why (capacity, distance, flood, insufficient clinics).
- Support variable K (1–5 in demo), vehicle capacities, travel-time threshold.
- Return proposed sites, vehicle-to-site assignment, demand assignments, KPIs and human-readable reasons.
- Compute a BASELINE: assign clinics to the K highest-population feasible barangays or sites (document exact rule). Use same restrictions and scoring for fair evaluation.
- Show side-by-side optimized vs baseline: covered high-priority residents, % priority-weighted coverage, unserved priority population, average road travel minutes, viable sites under scenario.
- Do not claim exact optimality if fallback heuristic used. Mark "Optimal (solver)" or "Heuristic (demo)" correctly.
- Deterministic: same snapshot+weights+scenario => same recommendations.
- Keep optimization on next-day proposed plan separate from today's published plan.
